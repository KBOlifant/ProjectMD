# What has changed in Project MD

A plain-language list of what was added and why. Newest first. Each item matches one commit.

## Coming next


## Design tab with colour swatches and font previews

- **Scans now keep their design and API data in a structured form.** Each scan saves the captured colours, fonts, radii, shadows, spacing, CSS variables, breakpoints and API calls as data (not just as text in the Markdown), and the server returns it with the scan, so the website can draw it. Older scans simply have none. One new nullable column was added to your database. The saved data is capped at 64 KB and any variable that looks like a secret is dropped. There is also an optional live test that scans a public site in-process and writes the result to a file, so the real pipeline can be checked without starting the server.

## Screenshots and animation detection

- **The results page has a Design tab.** Next to Preview and Raw there is now a Design tab that shows the site's design: the measured design system (colours, fonts, radii, CSS variables) and the AI's design breakdown. Preview shows the rest of the document. Copy and Download still give the whole .md file.
- **The AI now describes each animation and breaks down the design.** The image-reading call to Groq now writes a short description of every animation it finds (what moves, how and when, with a hint for rebuilding it) and a design breakdown: the overall style, how each font is used, what each main colour is for, and the components on the page (navigation, hero, buttons, cards, footer). It is given the measured fonts and colours so it names the real ones. The request was also made more reliable: it now asks Groq for a plain JSON object (shown working with images in Groq's docs) instead of strict schema mode, waits up to 60 seconds, and has room for a longer answer. When it does not run, the backend terminal now says why (screenshots taken, call skipped, or Groq's error type and the setting it objected to), without logging any page content.
- **The AI now lists the animations on a page.** In `ai` mode the scanner sends the first screenshot and the scroll screenshots (laid out in one or two grid images, because Groq takes at most 3 images) to Groq's image-reading model `qwen/qwen3.8-27b`, together with the animation facts the browser measured. It answers with a short summary and a list of animations (where, what moves, when it runs, which library, and a hint for rebuilding it), each marked *measured* (it matches timing data from the browser) or *inferred* (read from the pictures only, so it may be wrong). The scan document gets a new "Motion and animation" section. This is a second AI call per scan, with the same rules as the first: cached for repeat pages, checked against the daily limit first, and a failure just leaves the section out. The text notes still use `openai/gpt-oss-20b`, which cannot read images. Tested with a pretend Groq server only; no real call has been made yet.
- **The scraper now takes screenshots, loads images and measures animations.** Scans open the page in a desktop-sized window (1440 x 900), load images and fonts (through the same safety checks as everything else, with their own size limit), and take 6 screenshots while scrolling down with real mouse-wheel scrolls so smooth-scroll sites move. Before and after scrolling the scanner reads which animation libraries the page uses (GSAP, ScrollTrigger, Lenis, Three.js, Lottie, Barba and more) and the animations the browser is running, with their real durations and easing. Sites that answer with a bot check (such as Cloudflare's "Attention Required" page) now stop with a clear message instead of being documented. Every setting is in the new `Motion` section of `backend/ProjectMD.Api/appsettings.json`, explained in `docs/SCANNER-SETTINGS.md`. The overall scan time limit went from 45 to 75 seconds and the daily AI limit per person from 20,000 to 60,000 tokens to make room for this.

## Working with Claude

- **Added a set of review and planning helpers for Claude (from the open-source ECC project).** Claude now has 15 specialist helpers in `.claude/agents` (planning, design, code review, security review, test-first coding, C# and TypeScript/React review, build-error fixing, browser testing, hunting silent failures, tidying and docs) and a set of coding rules in `.claude/rules/ecc` (general, C# and TypeScript) that it follows automatically when working in this project. Nothing in the app itself changed. No automatic scripts ("hooks") were installed. *Why:* so Claude plans first, writes tests, and has its work reviewed the same way every time.

## Website and server connected

- **Added a "Copy API token" button for testing (development only).** When the website runs with `npm run dev`, the account menu shows a button that copies a fresh sign-in token to the clipboard, ready to paste into the server's Swagger page. The button is not included in production builds, and the token is never shown, stored or logged by the page.
- **Website takes your role from the server and has an Admin page.** In server mode the website now asks the server who you are and what your role is, instead of trusting the sign-in token, and never gives more than read-only access if the server cannot be reached (it shows a notice with a Retry button). Admins get an Admin link and a Users page where they can change other people's roles, with clear messages for the safeguards (you cannot change your own role, and there must always be one admin). The server side of this is still to come, so it was tested against a stand-in server.
- **Connected the website to the server.** The website can now run in two modes. In the default mode it works on its own with sample data stored in the browser, exactly as before. In "server mode" (turn it on with `NEXT_PUBLIC_SCAN_PROVIDER=api` in `frontend/.env.local`, and start the backend) scans, history and the monthly allowance come from the server and follow the person to any device. The website sends the person's Firebase sign-in with each request and shows plain messages when something goes wrong ("Verify your email to continue", "You've used this month's scans", "Can't reach the server"). The History page shows a Retry button if loading fails, and no longer flashes "No scans yet" while loading. *Why:* so scans belong to the person, not the browser. Tested against a stand-in server, not the real one yet.

## Backend server

- **Fixed builds failing because an old server was still running.** An old copy of the server kept its files locked, so new builds failed and the app kept answering with the old behaviour (which is why a scan still showed the old layout). The server now builds into a separate `backend/artifacts` folder that the old copy is not holding, so `dotnet run` builds the current code. The old server must still be stopped (or the computer restarted) if it keeps answering on port 5080.
- **Groq now returns a small structured answer, and the server lays out the Markdown document.** Groq is asked for a short JSON answer (overview, architecture notes, a one-line purpose for each endpoint, design notes, developer tips) with strict length limits; endpoints go to it as short ids so it cannot invent any. The server then builds the document in a fixed layout: a header block, tech table, API endpoints table with response shapes, third-party services, design tokens, page outline and tips. Everything the AI writes is cleaned so it cannot add links, HTML or headings, and a bad answer falls back to the free document. The answer memory now stores the small JSON, so repeats still cost nothing. The results page now shows tables and code blocks properly. Untested against the real Groq service so far.
- **Scans now summarise the site's design system.** After the page loads, the server samples what is on screen and records the main colours (with a guess at each one's role), fonts with their sizes and weights, corner radii, shadows, spacing steps, the CSS variables declared on the page root, breakpoints, and whether the site is built on Tailwind. It only reads styles, never page text, cookies or form values, and a failure never stops a scan. The summary stays under about 1.5 KB.
- **Scans now record the API calls a page makes.** While the page loads, the server notes each data request (method, path pattern such as `/api/users/{id}`, status codes, and the layout of the JSON as field names and types), lists GraphQL calls by operation name, and groups third-party services (analytics, fonts, payments...) separately. It never keeps response bodies, cookies, header values, query values or any real data; tests plant marker strings and check none leak. Changes in the API change the page's cache fingerprint.
- **Added a Swagger page for testing the server by hand.** With the server running in Development, open http://localhost:5080/swagger to see every endpoint (health, me, scans, admin users) and try them from the browser. It is switched off in Production. Protected endpoints still need a sign-in: the page has an Authorize button where you paste your Firebase token. Three new tests check the page loads, lists the endpoints and does not weaken the sign-in rules.
- **Connected the server to Groq (model `openai/gpt-oss-20b`).** With `Scanner__Mode=ai` and a Groq key in `backend/.env`, each scan now makes one request to Groq and uses the answer for the written overview. To keep costs down, the model is told to think briefly (its hidden thinking is billed too), the answer length is capped with a little extra room for that thinking, and the daily limits count the same total. A cut-off or empty answer, or a refused or failed request, falls back to the free document instead of retrying in a loop. Without a key, scans still work and carry a note that AI writing is not configured. The key is never logged or written to git. Tested with a pretend Groq server only; no real call has been made yet.
- **The backend now starts with just `dotnet run`.** Typing `dotnet run` in the `backend` folder works: a small launcher project there forwards to the real server, which starts on http://localhost:5080. (Before, you had to add `--project ProjectMD.Api`.) To build or test, use `dotnet build ProjectMD.sln` / `dotnet test ProjectMD.sln`. The README also explains the "file is locked by ProjectMD.Api.exe" build error: it means an older copy of the server is still running and needs to be stopped.
- **Clearer message when the database setting is not found.** The server keeps the database address in a private setting that is only read in Development mode. Starting it another way (for example from some editors, or without the launch settings) hid that setting and gave a confusing error. The message now says which mode it is in and how to start it correctly: `dotnet run --project ProjectMD.Api` from the `backend` folder.
- **Roles now live in your own database.** The server decides who is a viewer, member or admin and saves it in your database; anything a sign-in token claims about roles is ignored, so nobody can promote themselves. Your email is in a private admin list, so you become admin when you sign in with it after verifying it. Admins get server addresses to list users and change roles, with safeguards: nobody can change their own role or remove the last admin. If the database cannot be reached the server refuses the request instead of guessing a role. Note: someone on the admin-email list who is demoted on the Admin page is promoted again within about 30 seconds, so also remove their email from the list. About 35 new tests.
- **Added the AI step, built to use as few credits as possible (not connected to Groq yet).** The server can now run in `ai` mode: it sends the AI only a small, ranked summary of the page (about 3,000 tokens at most) and asks for a short answer (700 at most), one request per scan. Answers for unchanged pages are remembered for 7 days so they cost nothing. There is a daily limit per person (20,000 tokens) and overall (200,000), recorded from real usage. If the AI is off, not set up, or over its limit, you still get a useful free document built without it. No Groq code or key exists yet. The two new database tables are written but not created in your database yet.
- **Added real page fetching with Playwright (switched off by default).** In `extract` mode the server opens a public page in a real browser, strips it down to the useful text, headings, links and technology clues, and builds the tech list with plain rules (45 technologies) instead of the AI. The browser is locked down so it can never reach private or internal addresses: every request and every redirect is checked, and the browser itself has no network access of its own. Playwright's browser must be installed separately (the README explains how). Tested on sample pages and a local test site; not yet on a wide range of real sites.
- **Created the database tables and checked the real server.** The users and scans tables now exist in your Aiven PostgreSQL database, created from the setup script. The server was started against it: the health check reports the database as up, requests without a valid sign-in are refused, and your website address (port 3000) is allowed to talk to it. Nothing was saved yet because nobody has signed in through it.
- **Stopped "clear history" from resetting the monthly limit.** Clearing history now hides scans instead of erasing them. Hidden scans disappear from the person's list but still count toward the 10 scans a month, so nobody can create and clear over and over to get around the limit. This matters once each scan costs real money to generate. The database setup script was rewritten to include this (it had not been run yet). About 20 new tests check it.
- **Added the scans part of the server.** The server can now create a scan, list a person's scans, open one, and clear their history. Each person only ever sees their own scans (someone else's scan looks like it does not exist). Before anything is saved the web address is checked and refused if it points at a private or internal machine, so the app cannot be used to poke around inside a network. Each person gets 10 scans a month, and a limit on how fast they can start them. The scan content is still the made-up sample data, produced in one place so the real AI (Groq) can replace it later. *Why:* history and limits have to live on the server, not in the browser. About 185 automatic tests cover the address checks, limits and privacy between users.
- **Added sign-in checks and role rules to the server.** The server now checks that every request comes from someone signed in with Firebase, and applies the same viewer / member / admin rules as the website (starting a scan needs a verified email). A request with no valid sign-in is turned away, and a refused request says why (for example "verify your email"). There is also a "who am I" address (`/api/me`) that returns your email, role and scan usage. *Why:* the website's rules can be bypassed by anyone with browser tools, so the server has to enforce them too. About 130 automatic tests check the rules. Giving people the admin or viewer role is not possible yet.
- **Created the backend server project and database layout.** A C# server (ASP.NET Core) now exists in the `backend` folder. It describes two database tables, users and scans, and has a health-check address (`/api/health`). The database address and password are kept in a private setting on your computer, never in the code. The first database setup script is written but has not been run yet. *Why:* the website needs a real place to store accounts and scans.
- **Added instruction files for the backend server work.** Documents that tell the helper agents what to build on the server and how the website will talk to it. No app code.

## Sign-in and accounts

- **Stopped installed packages (node_modules) from showing up as changes.** A root `.gitignore` now tells git to ignore `node_modules` (and `.env` files), and the 182 package files that had been committed by mistake were removed from git's tracking. Nothing was deleted from your computer; running `npm install` recreates the folder. The packages stay in git's older history.
- **Show who is signed in and limit actions by role.** A menu shows your email, role and a sign-out button. People who have not verified their email see a banner and cannot start scans. Read-only users cannot start scans or clear history. A failed scan now shows what went wrong and a Try again button.
- **Added login, sign-up, forgot-password and verify-email pages.** New people can create an account, get a verification email, and reset a forgotten password. The pages never reveal whether an email already has an account. *Why:* scans should belong to a person.
- **Fixed a build error in the scraping test file.** The app failed to build because of one setting; raising it fixed the build. Nothing changed for users.
- **Kept scan data in one place and gave each user their own history.** The app now gets new scans from a single function, so the sample data can later be swapped for the real server. History is saved per account, so people sharing a browser no longer see each other's scans.
- **Added Firebase sign-in and split the app into signed-in and signed-out areas.** Email and password sign-in through your Firebase project. Pages that need an account send you to the login page when you are signed out.
- **Added user roles and permissions.** Viewer, member and admin, with a rule that starting a scan needs a verified email. New users are members. Unknown roles are treated as viewer, the safest choice.
- **Added instruction files for the sign-in and login work.** Documents for the helper agents. No app code.
